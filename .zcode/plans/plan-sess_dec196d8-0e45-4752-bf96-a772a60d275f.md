## 适配后的架构认知
你的 `_shared/moduleRegistry.ts` 已是单一真相源（prompt/执行器/MCP 都从它派生）。MCP server 已有 `<mod>_list/_search/_get` 只读工具。所以本方案**全部从 registry 派生**，不另起硬编码 map。

## A. 共享只读读取器 `_shared/dataReader.ts`（新增，复用 MCP 思路）
- `listModuleRecords(sb, moduleKey, {date_from?, date_to?, filters?, limit?})`：从 registry 取 `table`+`dateField`+可过滤字段 → `select("*")`+日期范围+ilike/eq+limit。用 **userSb（RLS 自动隔离本人）**。
- `getTodayPlan(sb, userId, dayStartHour)`：按偏移算今天，拉 daily_tasks 关联 todo 标题。
- （mcp-server 现有 `_list` 可后续迁移复用，本次不动它以免破坏。）

## B. ai-chat agent 化（`ai-chat/index.ts`）
- 加 **2 个工具**（少而精，利于模型 tool-calling）：
  - `read_data(module, date_from?, date_to?, filters?, limit?)` — 通用读，module 枚举=registry 的 21 个 key。
  - `get_today_plan()` — 今日已规划。
- **agent 循环**（≤5 轮）：带 tools 调 LLM → 有 tool_calls 则服务端执行（dataReader + userSb）→ role:"tool" 回灌 → 直到最终 JSON 操作。**降级**：API 拒绝 tools → 不带 tools 重试（退回单轮）；超 5 轮 → 强制收尾。
- fortune 模式不进 agent。

## C. registry 增量（写入增强，几乎零执行器代码）
- **todo 子条目**：todo ModuleDef 加字段 `parent_title` + `executor.resolves = {from:"parent_title", toColumn:"parent_id", targetTable:"todos", targetField:"title"}`。现有通用 `resolves` 机制自动解析（同 project_name/course_name）。再确认/补齐 `resolves` 在 update/delete 的 match 里也生效（让子项改/删可用）。
- **daily_task 按 id 引用**：daily_task ModuleDef 加可选字段 `todo_id`（prompt 会自动展示）；special 执行器分支接受 `todo_id`（有则直接用+去重，无则走标题找/建）。
- **dateField**：给各模块在 registry 标注 `dateField`（finance→date, schedule→start_time, civil_plan→plan_date…），供 read_data 日期过滤（单一真相源）。

## D. 提示词（仍由 registry 生成）
在 `buildSystemPrompt()` 加一段 `PROMPT_AGENT` 脚手架：说明 read_data/get_today_plan 何时用、语义匹配→命中用 daily_task(todo_id)/未命中建新+加今天、推荐→读后 summary 建议、最终仍输出纯 JSON 操作。

## E. 部署
`supabase functions deploy ai-chat --no-verify-jwt`（_shared 文件随之上传）。构建+typecheck。

## 为什么这样更优雅（对比旧方案）
- read 不再硬编码 map，**从 registry 派生**（和你 MCP 一致）。
- 写入增强主要靠 registry 的 `resolves`/字段，**执行器几乎不动**。
- 单一真相源：加新模块只改 registry，prompt+读+写全自动跟进。
